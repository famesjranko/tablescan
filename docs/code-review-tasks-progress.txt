## CR-004: Improve exception handling specificity
**Decision: SKIP (Valid Design Choice)**
**Date:** 2026-03-11

### Analysis
The code review identified broad `Exception` catching in three extractors:
- `vision_extractor.py:135-139`
- `camelot_extractor.py:128-135`
- `pdfplumber_extractor.py:150-154`

### Findings
**The exception handling implements a deliberate two-tier logging architecture:**

#### Tier 1 - Individual Extractors (DEBUG level):
All three extractors follow the same pattern:
```python
except ValueError:
    raise  # Re-raise page out of range errors
except Exception as e:
    logger.debug(f"[Extractor] Extraction failed for {pdf_path} page {page_num}: {e}")
    return []
```

#### Tier 2 - MultiExtractor (`multi_extractor.py:79-84`, WARNING level):
```python
except Exception as e:
    logger.warning(f"[MultiExtractor] {extractor.name} failed: {e}")
    all_results.append((extractor.name, []))
```

### Why This Design Is Valid

1. **Two-tier logging provides appropriate visibility:**
   - DEBUG in extractors: Silent in normal operation, available for troubleshooting
   - WARNING in MultiExtractor: Visible during normal operation, alerts operators

2. **Graceful degradation is essential:**
   - PDF parsing libraries throw unpredictable exceptions based on file content/corruption
   - One extractor failing shouldn't crash the entire pipeline
   - Empty results are valid return values (no tables found)

3. **Specific exceptions would be problematic:**
   - **Camelot**: `CamelotException`, `PDFSyntaxError`, `OSError` (poppler), etc.
   - **pdfplumber**: `PDFSyntaxError`, `PDFPasswordIncorrect`, `PDFTextExtractionNotAllowed`, etc.
   - **img2table**: OpenCV exceptions, Tesseract exceptions, image processing errors
   - Catching all specifically creates maintenance burden and risks missing edge cases

4. **Critical exceptions are handled correctly:**
   - `ValueError` for page out of range is re-raised (proper error propagation)
   - `FileNotFoundError` is raised before try block (line 99-100 in each)
   - `KeyboardInterrupt`, `SystemExit` are `BaseException`, not caught by `Exception`

5. **No silent failures:**
   - All exceptions are logged (DEBUG or WARNING depending on level)
   - Context is included: file path, page number, exception message

### Conclusion
The broad exception handling is an intentional, well-documented design choice for resilience in a multi-extractor pipeline. No changes needed.

## CR-005: Optimize _score_regularity performance
**Decision: FIX (Vectorize iterrows)**
**Date:** 2026-03-11

### Analysis
The code review identified `df.iterrows()` in `scorer.py:257-261` as potentially slow for large tables.

Original code:
```python
row_fill_rates = []
for _, row in df.iterrows():
    non_empty = sum(1 for cell in row if str(cell).strip())
    row_fill_rates.append(non_empty / cols if cols > 0 else 0.0)
```

### Evaluation

**Typical table sizes:**
- PDF tables are typically 5-100 rows, 3-15 columns
- Test fixtures use 3x3 tables
- Even "large" PDF tables rarely exceed 500 rows

**Performance reality:**
- For 100-row table: iterrows ~1-10ms, vectorized ~0.1-1ms
- Total extraction time: 1-10 seconds (YOLO, Camelot)
- Scoring overhead is negligible in both cases

**Is this a bottleneck?** No. The real bottleneck is PDF-to-image conversion and YOLO inference.

### Rationale for FIX (despite minimal performance impact)
1. `iterrows()` is a known pandas anti-pattern and triggers PerformanceWarnings
2. Vectorized operations are pandas-idiomatic and widely understood
3. The change is simple and equally readable
4. Other iterrows() calls exist in `_score_header_detection` (lines 357, 373) but those iterate over `data_rows` (excluding header), which is typically very small

### Resolution
Replaced iterrows with vectorized pandas operations:
```python
# Factor 3: Row fill consistency (vectorized for performance)
non_empty_per_row = (df.astype(str).apply(lambda col: col.str.strip() != '')).sum(axis=1)
row_fill_rates = (non_empty_per_row / cols).tolist() if cols > 0 else []
```

### Verification
- All 28 scorer tests pass
- Manual verification confirms identical results
- The two remaining iterrows() calls in `_score_header_detection` are kept as-is (operate on smaller data_rows subset, code clarity preferred)
